# Shared app implementation contract

Implements the user-approved deployment review: owned Supabase with a VPS/Vercel website, one published iPhone app, one active server/user per installation. No separate managed-account login is required. Local implementation is authorized; no production deployment or App Store publication is part of this change.

## Relay wire protocol (version 1)

The trusted endpoint is compiled into the app, never taken from the chosen server. Default: `https://salebell.vercel.app/api/push-relay`. The managed web endpoint forwards to its own Supabase `push-relay` function only when `SALEBELL_PUSH_RELAY_ENABLED=true`. Self-host installations do not deploy/operate this relay; `deploy/relay/schema.sql` is applied only by the managed operator. All requests are bounded JSON POSTs; all failures are sanitized.

- `enroll`: `{action,installation_id,control_secret,token,environment}`. UUID installation ID and random 32-byte hex control secret live only in phone Keychain. Existing verified same-token credentials return `{enrolled:true}`. Otherwise return 202 `{challenge_id}` and send a generic APNs challenge carrying `relay_enrollment:{installation_id,challenge_id,challenge}`. The challenge is random, expires, and never returned over HTTP. No token takeover without proving receipt. Requests for an existing installation ID must authenticate its control secret.
- `confirm`: `{action,installation_id,control_secret,challenge_id,challenge}`. Atomically proves token possession and enrolls installation; returns `{enrolled:true}`. Reject wrong/expired/consumed challenges. Token ownership may move only after this proof; revoke the previous installation atomically. Do not reset an existing installation's revision on enrollment.
- `activate`: `{action,installation_id,control_secret,revision,backend,user_id,route_id,capability,content_key}`. backend is canonical HTTPS API origin; IDs are UUIDs; secrets are random 32-byte hex. revision is a positive safe integer, durably incremented by phone before network work. Only strictly newer revisions may change a route. Exact same-revision retries are idempotent; differing same/lower revisions fail. Returns `{route_id}`. Activation expires in 30 days and is refreshed on registration.
- `revoke`: `{action,installation_id,control_secret,revision}`. Newer revision atomically invalidates capability; identical already-revoked retry succeeds. Returns `{revoked:true}`. Works independently of customer backend availability.
- `deliver`: `{action,capability,notification_id,title,body}`. UUID notification ID, title <=200 and body <=1500 characters. Resolves exactly one active unexpired route by SHA-256 capability hash, rate limits fail closed and deduplicates notification IDs per route. Sender supplies no device token, user/recipient list or APNs topic. Returns `{sent:1,failed:0}` or sanitized rejection. No broadcast fallback.

Install control secret and delivery capability are different credentials. Store hashes at rest, with the AES content key/token only in the private relay schema. No ordinary client or customer backend can read installation credentials or another user's capabilities. Self-hosted backend registration derives `auth.uid()` and stores only that user's delivery capability as its relay device `token`, with `transport=relay`; separate privately built clients can use `transport=apns`. Current workspace member/sandbox selection remains authoritative. Both Apple/Google/test dispatch use this transport. When managed relay mode is enabled, **all** managed direct APNs sends are blocked, including old tokens that have not enrolled yet. Older managed app builds must update; this deliberate compatibility break prevents stale registrations from bypassing revocation during migration.

## Notification privacy

APNs expiration is zero. Its visible fallback is generic (`Salebell` / `Open Salebell to see your latest activity.`); sale text is AES-256-GCM encrypted with the route content key. Payload: `relay_route_id`, `relay_encrypted:{nonce,ciphertext}` (base64; ciphertext includes GCM tag), `aps.mutable-content=1`, sound `chaching.caf`. A Notification Service Extension enriches only when the shared active route ID matches and the route key decrypts. Unknown/revoked routes retain generic content and no sound/badge. Enrollment challenges never display sale data. Foreground and tap callbacks reject obsolete route IDs. Apple-accepted pushes cannot be recalled; generic late alerts remain possible if iOS does not run the extension.

## iOS interfaces

`ServerConfiguration`: Codable, Equatable, Sendable; `siteURL:URL`, `supabaseURL:URL`, `supabaseKey:String`, stable `identity:String` derived from canonical API origin, `cloud` uses original build defaults. Validate HTTPS origins (DEBUG loopback exception), reject service-role/secret keys including legacy JWT role. `ServerConfigurationStore` shares selected config and a selection generation with widget. Supabase client uses explicitly scoped Keychain service; do not import an old session into a different backend. Widget discards fetches if selection generation changes.

`@MainActor final class PushRelayClient` (root owns implementation), initializer accepts `configuration:ServerConfiguration`; `func register(token:String,environment:String,userID:UUID) async throws -> String` returns capability, `func revoke() async throws`, `func handleEnrollment(_ userInfo:[AnyHashable:Any]) async -> Bool`, `func accepts(_ userInfo:[AnyHashable:Any]) -> Bool`. Singleton shared enrollment coordinator supports delegate delivery while registration waits. Installation control state is global across backends and durable in Keychain; one actor/MainActor sequence drains pending activation/revocation before replacing a route. Shared notification route storage is cleared before revoking and published only after activation succeeds. Enrollment waits boundedly for foreground Apple challenge; subsequent attempts retry.

`SupabaseBackend(configuration:)` owns a relay client. Registration obtains current Auth user, calls relay register and RPC `register_relay_device(p_capability,p_apns_environment,p_app_version)`. Add `Backend.stopPushDelivery() async throws` with default no-op for demo/test backends; Supabase implementation revokes centrally. AppModel drains registration, invokes this before local sign-out/backend switch/deletion, best-effort removes old backend registrations for relay transport (cannot block switch on offline old backend), clears old session/widget/notifications. Automatic auth loss clears shared active route immediately, revokes, and blocks new route activation until revocation succeeds. AppModel exposes mutable backend, selected configuration, generation; old auth/data requests cannot modify new state. Server settings are available signed-out and signed-in. Root view/tasks are keyed by backend generation.

## Work and verification

1. Relay schema/handler: SQL atomic ownership, monotonic revisions, expiry, revocation, dedupe; unit tests for malformed requests, stolen tokens/challenges, stale writes, revoked capability, limiter failure and sanitization.
2. Backend migration/dispatch + managed proxy: prove membership/RLS, token transport separation, exact one-device relay delivery, expired/revoked rejection and direct-send exclusion.
3. Runtime iOS settings/session/widget: tests URL/key validation, identical user UUID on two origins, stale auth callbacks, selection generation and sign-out/switch failure behavior.
4. Phone relay client/extension: control state durable before requests, challenge receipt and bounded wait, generation filtering, encrypted content tests, app/extension compilation.
5. Integrate and review: root and web tests, SQL migration/relay tests, web lint/build, iOS simulator build/tests, installer release regeneration. Document managed relay setup and physical-device production APNs checks still required. Preserve the user's existing deployment edits; do not commit/push/deploy without an explicit request.
